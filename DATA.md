# How the two deliverables correspond

This work ships as **two packages that are staged together from the same source revision**:

| | GitHub package | Zenodo package |
|---|---|---|
| what it is | the maintained repository tree | the versioned archival snapshot |
| contains | source, documentation, environment, configs, checks, figures, the approved Figure 1 source, the frozen protocols and the complex table | **everything in the GitHub package, byte for byte**, plus the frozen arrays and results |
| size | tens of MB | hundreds of MB |
| purpose | read, clone, contribute, re-run the checks | reproduce every reported number without retraining |

`PACKAGE_INFO.json` in each package records the **same `source_revision`** and the **same
`version`**. That is the correspondence: a Zenodo archive is only valid against the GitHub tree whose
revision it names, and the staging script refuses to finish if any file shared by the two trees
differs between them.

## Why the split

The frozen arrays — contact labels, masks, every stored prediction, the per-complex metric arrays —
are binary `.npz` files that `.gitignore` deliberately keeps out of the repository. They are not
optional extras: **without them nothing can be reproduced**, because the reported numbers are
computed from stored predictions rather than regenerated by retraining. Hence the archive.

Files the repository's `.gitignore` excludes but the Zenodo package includes:

```
data/processed/*.npz          contact labels, masks, residue graphs
results/tables/**             stored predictions, per-complex metrics, aggregates, MD tables
results/review/**             the control, sweep, sensitivity and comparator analyses
figures/previous_versions/**  superseded figure versions, kept as provenance
```

`data/processed/complex_metadata.tsv` and `data/splits_v2/protocols.json` are **also** in the GitHub
package, even though they are data, because they are small, textual and are the definition of the
benchmark.

## Using them together

Unpack the Zenodo archive over a clone of the GitHub tree, or simply work inside the Zenodo
archive, which is a superset:

```bash
tar xzf tcr-imap-zenodo-<version>.tar.gz
cd tcr-imap-zenodo-<version>
sha256sum -c CHECKSUMS.sha256          # every file, including the frozen arrays
python tests/test_frozen_artifacts.py
python scripts/worked_example.py
```

Or, from a GitHub checkout:

```bash
tar xzf tcr-imap-zenodo-<version>.tar.gz --strip-components=1 \
    -C <checkout> tcr-imap-zenodo-<version>/data tcr-imap-zenodo-<version>/results
```

Check that `PACKAGE_INFO.json` reports the same `source_revision` in both before mixing them.

## What is in neither

| not included | why | how to get it |
|---|---|---|
| `data/structures/`, `data/raw/` (917 MB) | third-party structures; redistribution is unnecessary and the terms are not ours to grant | `data/SOURCES.md` and `THIRD_PARTY_NOTICES.md`: STCRDab IMGT-numbered structures, retrieved 15 August 2026, and the Protein Data Bank |
| `md/runs/` (7.7 GB) | molecular-dynamics trajectories | available from the corresponding author on reasonable request; analysis outputs are included |
| `md/systems/*/charmm-gui*` (3.3 GB) | CHARMM-GUI build bundles | rebuild from `md/systems/BUILD_MANIFEST.tsv` at charmm-gui.org |
| `results/checkpoints/` (160 MB) | trained weights from the **superseded** 28-position candidate set, under partitions that are not the frozen protocols. They are not the reported runs and reproduce nothing | nothing to retrieve; `results/review/FR4_CHECKPOINT_AUDIT.md` explains why no usable checkpoint exists |
| `results/tables/_partial/p82v1/`, `_partial/p84v2/24b_run_all/` | resume shards of a superseded generation and of the pairwise runner | regenerated by retraining; no reported number depends on them |
| the manuscript and SI documents themselves | not published; distributing them is a publisher-rights question, not a reproducibility one | the **build assets** are included — the builders, the caption source and the SI table generators — so both documents can be rebuilt |
